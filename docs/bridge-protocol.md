# Extension Bridge Protocol v6

Spec coverage: S2 (bridge PoC), S5 (NDJSON over stdio, upstream `modes/rpc` framing). S3 is the acceptance context: unmodified upstream example extensions must work "wie gewohnt" for the headless-safe API slice through this protocol.

Upstream pin: earendil-works/pi @ `17d6ca7` (shallow clone at `upstream/`). All upstream paths below are relative to `upstream/`. Types referenced by name are reused verbatim from the cited file; they are not re-specified here.

## Overview & topology

Two processes, one stdio pipe pair:

- **Core (Rust)** — owns the agent loop, model runtime, built-in tools, and session storage. It is the **RPC client**: writes command lines to the sidecar's stdin, reads responses and events from its stdout.
- **Sidecar (Node)** — runs the **original, unmodified upstream extension loader** (`core/extensions/loader.ts`) and `ExtensionRunner` (`core/extensions/runner.ts`). It is the **RPC server**: dispatches received events to extension handlers and reports results.

The sidecar never talks to a model; the core never loads TypeScript. Everything an extension observes happens inside the sidecar; everything that mutates session/model state happens in the core.

## Framing

NDJSON over stdio, reusing upstream rpc-mode framing verbatim:

- One JSON object per line. Records are delimited by `\n` only; payload strings may contain any other Unicode separator (`upstream/packages/coding-agent/src/modes/rpc/jsonl.ts:10-13`). A trailing `\r` on a line is stripped; a non-empty buffer at stream end is emitted as a final record (`jsonl.ts:21-58`).
- **core→sidecar commands**: `{ id, type, ...payload }`, `id` = UUID generated by the core (`rpc-types.ts:20`, `RpcCommand`).
- **Sidecar→core responses** to commands: `{ id, type: "response", command: <type>, success: true, data? }` or `{ id, type: "response", command: <type>, success: false, error: string }` (`rpc-types.ts:112-245`, error variant at `:245`).
- **Sidecar→core events**: standalone typed JSON lines, no `id`, no response expected (precedent: `AgentSessionEvent` streaming via `toJsonEvent` at `rpc-mode.ts:363`).
- stdout is protocol output only; both processes must keep logs on stderr.
- Malformed line: sidecar answers `{ id: null, type: "response", command: "parse", success: false, error: "Failed to parse command: …" }` (`rpc-mode.ts:770-781`).
- Unknown command `type`: `{ success: false, error: "Unknown command: <type>" }` (`rpc-mode.ts:734-737`).
- Events are the upstream event objects as JSON. Fields that are not JSON-serializable in the upstream type (e.g. `AbortSignal` on session-boundary events) do not occur in the v0 catalog; any such field is omitted on the wire.

## Handshake

1. Core spawns the sidecar with clean stdin/stdout.
2. Core sends `init`: `protocolVersion: 6` plus the core capability set — which `extension_ui_request` methods the core implements (TUI adds `custom`, § Custom pane) and the blocking-command timeout — and, when `<agent-dir>/mcp.json` exists, its content as `mcpConfig` (MCP §):

   `{"id":"…","type":"init","protocolVersion":6,"capabilities":{"ui":["select","confirm","input","editor","notify"],"timeoutMs":30000},"mcpConfig":{"mcpServers":{"docs":{"command":"docs-server","args":[],"exposure":"direct"}}}}` (TUI: `ui` gains `"custom"`)

   The `ui` list decides the extension UI mode (WP-505): non-empty → the sidecar wires the dialog UI context (`ctx.hasUI === true`, dialogs round-trip as `extension_ui_request`); empty → headless mode, the runner keeps the upstream noOp UI context (`ctx.hasUI === false`) and extensions take their upstream no-UI defaults (e.g. `permission-gate` blocks dangerous bash with `Dangerous command blocked (no UI for confirmation)`; `select`/`confirm` resolve to `undefined`/`false` without a dialog). The pi-rust v0 core is headless and sends `"ui": []`; a UI client (e.g. the M6 TUI) advertises its methods.

3. Sidecar rejects a non-six `protocolVersion` with an `init` error response and exits non-zero.
4. Sidecar loads extensions with the original loader, initializes `ExtensionRunner`, responds `success` with `data: { apiVersion: 0 }`, then emits the `ready` event.
5. **Capability negotiation**: `ready.events` lists the event names that have at least one registered handler. The core only sends events that appear in `ready.events` *and* in the core catalog below. An unknown or unsubscribed event is **logged and ignored, never fatal** (same rule in both directions).
6. The core enters state `running` only after `ready`. An `init` error or spawn failure leaves it `stopped` (no extensions, built-ins only).

`ready` payload (all fields JSON): `apiVersion: number`, `extensions: [{ path, hidden? }]`, `errors: [{ path, error }]` (from `LoadExtensionsResult`, `core/extensions/types.ts:2336`), `tools: [{ name, label, description, promptSnippet?, parameters, exposure?, defaultActive? }]` (subset of `ToolDefinition`, `core/extensions/types.ts:600`; `parameters` is the TypeBox schema as JSON; `exposure`/`defaultActive` new in v5) — the **initial snapshot**; post-ready changes arrive as `tools_changed` (v2), `activeTools: string[]` (the names active at ready, v5 — see Active tool set §), `commands: [{ name, description? }]` (from `RegisteredCommand`, `types.ts:1615`), `shortcuts: [{ key, description?, extensionPath }]` (upstream-resolved `ExtensionShortcut`s, v4) + `shortcutDiagnostics: string[]` (the conflict messages, v4), `flags: ExtensionFlag[]` (`types.ts:2135`), `providers: string[]` (names from `pi.registerProvider`, `types.ts:1907`), `events: string[]` (keys of `Extension.handlers`, `types.ts:2317-2335`).

## Decision-event semantics

- **Fast path**: if no handler is registered for the event, the sidecar answers immediately with `success` and `data: null` (mirrors `hasHandlers` in `runner.ts:265-275`).
- **`tool_call`**: sidecar runs `emitToolCall` — first handler result with `block: true` short-circuits (`runner.ts:1256-1274`); handlers may mutate `event.input` in place, with no re-validation (upstream contract, `types.ts:1253-1259`). The sidecar returns the **final** `input`, so the core executes the tool with the post-mutation arguments. Core: `result.block` → do not execute, record a tool result `Blocked by extension: <reason>`; `result.terminate` is honored only when every finalized result in the batch carries it (upstream rule, `types.ts:1481-1486`).
- **`tool_result`**: sidecar runs `emitToolResult`, which chains partial mutations and returns only the combined change or `null` (`runner.ts:1197-1254`). Core applies the returned fields to the recorded result; replacing `content` without `structuredContent` drops the structured content (upstream rule, `types.ts:1494-1503`).
- **`context` / `context_with_system`**: `context` is always answered with `data: null` (v0 no-op); the single `emitContext` runs on `context_with_system` — the core sends the full transcript and uses the returned conversation as-is for the provider request. This is net-identical to upstream's two-phase `emitContext` (`runner.ts:1312`). T4 resolution: the core does not send a separate phase-1 `context` command; extensions that subscribe only to `context` get their handlers routed through the `context_with_system` phase.
- **`input`**: transforms chain, `action: "handled"` short-circuits (`runner.ts:1532` onward). Core: `continue` → proceed with original input; `transform` → use returned `text`/`images`; `handled` → drop the input, no agent turn.
- **`before_agent_start`**: the core sends the trigger fields under `event` plus the currently rendered `systemPrompt` as a top-level field (the upstream event exposes it as a getter), and may additionally carry `systemPromptOptions` (`BuildSystemPromptOptions` JSON subset: `cwd`, `forceSystemPrompt`, `sections`, `selectedTools`, `skills`). The sidecar merges those fields with its `cwd` and `forceSystemPrompt` from `systemPrompt` into the options passed to `emitBeforeAgentStart`, then renders the final string: a handler's direct `forceSystemPrompt` mutation wins verbatim (claude-rules-style string rewrite); a structural mutation (`sections`/`selectedTools`/`skills`) renders through the upstream prompt builder (`buildSystemPrompt`, `core/system-prompt.ts`) with the base stand-in `forceSystemPrompt` suppressed so the sections appear in the prompt; with no mutation the final string is unchanged. Response `systemPrompt` is omitted unless the final prompt differs from the base; core: prepend the returned custom `messages`; if `systemPrompt` is present, it replaces the system prompt for this turn.
- **Dialog timeouts**: omitted dialog timeouts (including `editor`) use the `init`-negotiated `timeoutMs`.
- **`user_bash`**: `data: null` → core executes locally; `data.result` → core uses that `BashResult` verbatim; `data.operations` is not representable in the core and is treated as "execute locally" with an `extension_error`-style log line.

## Error & lifecycle model

- Every command that is not F&F gets exactly one response line matching its `id`; `success: true` carries `data?`, `success: false` carries `error: string`.
- A handler throwing inside the sidecar does not fail the command: the sidecar emits an `extension_error` line (with `extensionPath` `"<unknown>"` when the upstream emit path carries no per-handler identity) and the decision resolves to its default (`tool_call` → no block, input unchanged; `tool_result`/`context`/`context_with_system` → unchanged; `input` → `continue`; `before_agent_start` → no additions; `user_bash` → null; `session_before_compact` → proceed (no cancel, no extension summary)). Precedent: per-handler catch + `emitError` in `runner.ts`.
- **Sidecar crash (EOF or non-zero exit) is a transport error.** The core state machine:
  - `running` — handshake complete, sidecar alive.
  - `degraded` — transport error or a blocking command unanswered after the `init` timeout (`capabilities.timeoutMs`, default 30000 ms). Built-in tools and the agent loop keep working; extension tools from `ready.tools` are removed from the model's tool set (marked unavailable); pending decision events resolve to default-allow/no-op; in-flight `extension_ui_request` dialogs resolve to their upstream defaults (`confirm` → `false`, `select`/`input`/`editor` → `undefined`, per `createDialogPromise` in `rpc-mode.ts:95-137`); further core→sidecar writes are dropped and logged. v0 has no sidecar respawn: `degraded` is terminal for that instance.
  - `stopped` — clean shutdown (core sent `session_shutdown`, sidecar exited) or a failed handshake. Extensions unavailable, core standalone.
- Unknown or unsubscribed event names in either direction are logged and ignored, never fatal.
- The core correlates strictly by `id`; a response for an unknown or already-timed-out `id` is ignored.
- **Session truth**: the core owns session entries and persists them (v0: in-memory + JSONL file). The sidecar keeps only a minimal in-memory view (session name, last model) and never writes session files. `session_append_entry`, `user_message`, `set_model_request`, `set_thinking_level_request` are the only sidecar→core state mutations.
- **Bidirectional liveness**: both processes must keep reading stdin while awaiting responses — a sidecar handler may issue `tool_call_request` while an `extension_tool_call` is in flight. No head-of-line blocking in either direction.

## MCP servers (v2)

The sidecar hosts the **unmodified upstream built-in mcp extension** (`createMcpExtension`, `packages/coding-agent/src/extensions/mcp/`) on the shared runtime, so MCP behavior — client, naming, exposure, crash semantics — is the upstream code itself (`packages/mcp/`, NDJSON JSON-RPC over stdio, protocol 2025-11-25 negotiated against the server's supported list).

- **Server sources**: (a) `pi.registerMcpServer(name, config)` from any loaded extension (validated by upstream `validateMcpServerConfig`, stored in the runtime `McpServerRegistry`); (b) the `mcpConfig` init field — the core reads `<agent-dir>/mcp.json` (upstream shape `{"mcpServers": {...}}`, same validation; a missing file is omitted) and passes it verbatim. Each entry is registered through the same registry path; upstream rule: an `mcp.json` entry takes precedence over a same-name extension registration (last write wins per name; `-`/`_` namespace clash → init error). Project `<cwd>/.pi/mcp.json`: documented v0 non-goal (agent-dir only, same rule as `settings.json`).
- **Lifecycle**: the mcp extension connects on `session_start` (the core fires it after `ready`), lazily reconnects on the next call after a crash (upstream `McpServerConnection` state machine; no auto-restart), and disconnects on `session_shutdown`. Connection is asynchronous: MCP tools are **not** in the `ready.tools` snapshot and arrive via `tools_changed` once connected. The `before_agent_start` decision waits for servers whose configured exposure includes `direct` (upstream `startupWaitMs`, 10 s), so `direct` servers' tools are registered before the first turn's tool declarations are built.
- **Naming & dispatch**: tools are declared `mcp__<server>__<tool>` (upstream `naming.ts`) and reach the core through the ordinary extension-tool path (`tools_changed` → `extension_tool_call` → the mcp extension's tool wrapper → the connected server). The core additionally routes `mcp__*` names to the bridge even when the tool is not (yet) in the extension set: the sidecar answers `Unknown extension tool` and the run records an error tool result instead of aborting as a model-script error.
- **Exposure in v0**: all registered MCP tools are declared to the model regardless of the `exposure` field (the headless core has no codemode/tool_search; upstream's `codemode`/`deferred` discovery layers are unreachable). `exposure` still drives the upstream wait logic above.
- **Transports**: stdio (`command`/`args`/`env`) and remote HTTP (`url` + `headers`) — both are the upstream `createDefaultTransport` code (NDJSON JSON-RPC stdio; streamable-HTTP with `application/json` and `text/event-stream` response assembly). `headers` and `env` values support `$ENV_VAR`/`${ENV_VAR}` expansion (upstream `resolveConfigValueOrThrow`); the secret value is resolved in the sidecar and never appears in core or sidecar logs.
- **Timeouts**: the MCP client's per-request default (60 s) and the sidecar→core blocking-command timeout (`capabilities.timeoutMs`, default 30 s) are independent; a slow MCP tool call may outlive the core's `extension_tool_call` timeout, which degrades the bridge (Error & lifecycle model).
- **Out of scope (WP-703+)**: OAuth sign-in (`/mcp login`, the `oauth` config fields are accepted by validation but no auth provider is wired — a 401 surfaces as the server error), dynamic client registration, the `/mcp` TUI manager, resource tools beyond registration, `toolExposure` per-tool overrides (accepted by validation, single exposure used).

## Shortcuts (v4)

Extension `registerShortcut` (upstream `types.ts:1729`) reaches the TUI:

- **Resolution** (sidecar, at `ready`): the core sends its resolved keybinding table as `init.keybindings` (action → keys); the sidecar runs upstream `runner.getShortcuts(resolved)` — the exact upstream precedence: a **reserved** built-in on the key (the 18 editor-global ids, `runner.ts:98`) blocks the shortcut with a diagnostic ("conflicts with built-in shortcut. Skipping."); a **non-reserved** built-in is shadowed (extension wins, diagnostic); two extensions on one key → the later registration wins. `ready.shortcuts` carries the effective set; `ready.shortcutDiagnostics` the messages (the core logs them on stderr, upstream prints them at startup).
- **Dispatch** (TUI): `process_key` checks the extension shortcuts **first** (upstream `custom-editor.handleInput` does the same, before any built-in binding); a match consumes the key and sends `shortcut { key }`; the sidecar invokes the registered handler (same bridge context stand-ins as `command`); a handler error renders through the command-result event (upstream `showError` equivalent).
- **v0 non-goals**: post-ready `registerShortcut` (no upstream refresh hook exists either — ready-snapshot only), unregister (none upstream), the shortcut management UI, `/hotkeys` listing.

## Compaction (v3)

Context compaction per upstream `core/compaction` (auto-trigger only, v0):

- **Trigger**: at the top of each agent-loop turn, before the turn's model call, the core estimates the context size (upstream's exact heuristic: `ceil(chars/4)` per message, image blocks ≈ 4800 chars; a trailing estimate after the last assistant `usage` where present) and compacts when `contextTokens > contextWindow - reserveTokens` (defaults: reserve 16384, keep recent 20000). The context window comes from the model registry; runs without one (fake model) stay off unless the scenario supplies a `compact: { window, reserve, keep }` override. Upstream settings-file knobs (`reserveTokens`, `keepRecentTokens`, per-model overrides) are a v0 non-goal.
- **Cut point**: the core walks back from the newest entry accumulating ≥ `keepRecentTokens` (upstream `findCutPoint`): never inside a `toolCall`/`toolResult` pair; an assistant message with tool calls keeps its results. Entries before the cut are summarized; the cut entry becomes `firstKeptEntryId`.
- **Summary call**: the SAME active model driver, tools-less conversation = `[system SUMMARIZATION_SYSTEM_PROMPT, user "<conversation>…</conversation>" (+ "<previous-summary>…") ]` with the verbatim upstream prompts; the serialized conversation is upstream `serializeConversation` (`[User]` / `[Assistant]` / `[Assistant tool calls]: name(k=v)` / `[Tool result]` truncated at 2000 chars, thinking omitted). The call emits no `message_start`/`message_update`/`message_end`, no `model_delta`, and no `usage` session entry — the summary's usage lands in the compaction entry only. A tool call in the summary response or `stopReason: length` is a failure.
- **Events & entry**: `session_before_compact` (decision: cancel or extension-supplied summary → `fromHook`) → summary call → `session_compact` with the new entry: `{ type: "compaction", id, parentId, timestamp, summary, firstKeptEntryId, tokensBefore, usage?, fromHook?, systemMessage? }` (upstream `CompactionEntry` shape). Failure paths emit `session_compact_failed` (typed reason) and the turn proceeds uncompacted. Headless NDJSON gains the `compaction` / `compaction_failed` line kinds.
- **Projection**: the session transcript is compaction-aware for fresh runs and resume-from-file: a path containing a compaction entry projects to `[compactionSummary message] + entries from firstKeptEntryId to the compaction (minus system messages) + everything after` — the same projection upstream `buildContextEntries` applies, so pi-rust files with compaction entries load the way upstream loads them.
- **v0 non-goals**: split-turn (`TURN_PREFIX`) summaries, read/modified file-lists appended to the summary, overflow-retry (compact + retry once), the manual `/compact` command, per-model settings overrides, micro-compaction variants.

## Active tool set (v5)

The **active tool set** is the set of extension tools declared to the model (upstream: `getActiveTools`/`setActiveTools`, `types.ts:1827`; "the active tool set is the set declared to the model", `types.ts:535`). The sidecar owns the upstream semantics, the core applies them:

- **Initial activation** (at registration): `direct` and `model-only` tools activate, **unless `defaultActive: false`**; `codemode`/`deferred` do not; `hidden` never activates (upstream exposure rules, `types.ts:521-536`). `ready.activeTools` carries the initial set; `ready.tools` entries gain `exposure?` / `defaultActive?`.
- **`pi.setActiveTools(names)`**: replaces the active set; unknown and `hidden` names are ignored (upstream). The sidecar emits `tools_activated` (F&F) so the core's model-visible extension set = registered tools filtered to the active names. `pi.getActiveTools()` reflects the sidecar state.
- **Coalescing**: registration changes (`refreshTools`) and `setActiveTools` share one tick: at most one `tools_changed` + `tools_activated` pair per sidecar tick, carrying the final state; the core replaces its tool set then its active set, in that order. On `tools_changed`, the core prunes active entries for tools that no longer exist.
- **Built-in `tool-search`**: the sidecar hosts the upstream `tool-search` extension (upstream main.ts auto-loads it). Its `tool_search` tool registers inactive (`model-only`, `defaultActive: false`) — activation goes through `setActiveTools` (core-side `--tools`/`defaultTools` config is a v0 non-goal). Its BM25 ranker searches `codemode`/`deferred` tools and loads the matches via `setActiveTools`, so they become declared from the next turn — the wire path this section describes.
- **Execution routing is unchanged**: an extension tool call executes when its name is registered (the core's `run_tool` shadowing), independent of the active set; the active set only controls model declaration.

## Custom pane (v6)

`ctx.ui.custom` (WP-1006, the WP-707 tier-(b) descriptor subset): when the
core advertises the `custom` capability (TUI only; headless runs keep the
upstream noOp), the sidecar runs the factory's real pi-tui component
sidecar-side and relays a **structured descriptor** — the pane host never
renders ANSI, the TUI renders the descriptor in the transcript slot (above
the editor, below dialogs).

- Sidecar→core events (one-way; the sidecar's promise owns the result):
  - `pane_open { id, blocked?: { kind, message } }` — a pane opens.
  - `pane_update { id, title?, lines?: [{ text }], list?: { items: string[], cursor }, input?: { label, value, placeholder? }, blocked? }` — full descriptor snapshot (replacement, not patch); sent on `requestRender` and after keys, deduped by signature.
  - `pane_close { id }` — the component called `done(result)`; the TUI drops the pane. The result resolves the sidecar-local promise; it does **not** cross the wire.
- Core→sidecar: `pane_key { id, key: { code, text? } }` — a TUI key for the open pane. `code` ∈ `up | down | left | right | enter | escape | backspace | tab | char`; the sidecar encodes it to the pi-tui input string and dispatches it to the focused component (root `handleInput`, else the first `capturesViewportInput` descendant — the SelectList case — else any `handleInput` descendant).
- Descriptor subset = the WP-707 production shapes: title + plain lines + list with cursor + one input + `blocked`. Out-of-subset components degrade to their `render(width)` lines (ANSI-stripped); a throwing factory resolves `undefined` with a sidecar log — never a crash.
- The TUI never closes a pane itself: the component decides via `done`. While a pane is open, TUI keys route to the pane (not the editor).
- **Timeout contract (same as the dialog manager)**: a pane resolves with the upstream default (`undefined`) after `capabilities.timeoutMs` — the sidecar timer starts when the pane opens, i.e. after the core already sent the blocking command, so it always fires before the core's request timeout; an unattended interactive pane therefore degrades its command to a typed error instead of degrading the bridge.

## Out of scope for the v0 bridge

- **TUI renderers**: message/entry renderers, tool renderers, markdown transformers, themes, `ctx.ui` beyond the dialog subset (`select`, `confirm`, `input`, `editor`, `notify`, `setStatus`, `setTitle`, `set_editor_text`) plus the `custom()` **descriptor subset** (v6, Custom pane § above) — no full pi-tui component model (mouse, focus trees, overlays), no `onTerminalInput`, working indicators, widget factories, footer/header, autocomplete, editor-text readback.
- **`registerShortcut`**: accepted by the loader, ignored by the bridge.
- **Compaction**: the compaction events and the session entry are in (v3, Compaction §); still out: the manual `compact` command / TUI `/compact` wiring (auto-trigger only), and boundary mutation (`entries`/`continue` on `turn_end`, `agent_before_settle`); `turn_end`/`message_end` are delivered without their mutation results.
- **MCP**: stdio + HTTP/SSE transports, registration (config + extension), and tool execution are in (MCP §); OAuth sign-in, dynamic client registration, and the `/mcp` TUI manager are not (WP-703+).
- **Provider invocation (v1 limitations)**: extension-registered providers are invoked by the core (WP-701) for the legacy config form (`registerProvider(name, config)` with `streamSimple`) and the native `Provider` object form (WP-1005; the object stays sidecar-side, only the model list crosses the wire). The five oauth-capable upstream built-in providers (radius, kimi-coding, github-copilot, xai, meta) are exposed in the `providers` payload and stream through the upstream runtime (WP-1007), where the stored-credential refresh (5-minute validity margin) and rotated-token write-back run sidecar-side. `pi-rust auth login <provider>` runs the pinned upstream's terminal login flow unmodified (dedicated `sidecar/auth-login.mjs`, prompts relayed over NDJSON). Still out of scope: virtual models (`registerVirtualModel` is accepted and ignored), `apiKey` `!command` values (typed error), abort signals (no per-turn `AbortSignal` exists in the core loop yet), and oauth credentials consumed by the core's built-in drivers (typed error; the sidecar-routed models of those providers work).
- Remaining upstream events not in the catalog (`project_trust`, `resources_discover`, `before_provider_request`/`before_provider_headers`/`after_provider_response`/`provider_stream_event`, `session_before_switch`/`session_before_fork`/`session_before_tree`, `ui_prompt_start`/`ui_prompt_end`, `tool_execution_*`, `agent_settled`) are not sent; extensions that need them load, but their handlers never fire.
