- Sidecar hosts the callback: capture the config object at registration (models list verbatim as Model objects), call `config.streamSimple(model, transcriptContext, options)` directly on a core `provider_stream` request — no ModelRuntime/auth.json/oauth in the sidecar. apiKey resolution: literal + `$ENV_VAR` only.
- Protocol 701a: `ready.providers` becomes `[{name, models:[{provider,id,api,...}]}]` (was name-only); new core→sidecar request `provider_stream {streamId, model, messages, options}`; sidecar→core lines `{type:"provider_stream_event", streamId, event:<upstream AssistantMessageEvent JSON>}`; terminal `done`/`error` events end the stream. Bridge version bump + spec section in docs/bridge-protocol.md.
- Core 701b: per-turn selection — model id in extension model list ⇒ bridge stream path (before the hardcoded OpenAi/Anthropic/Google/Bedrock match); `text_delta`→on_delta, `toolcall_end`→tool_calls, `done`→AssistantTurn, terminal `error`→Err(errorMessage) (existing error surfacing agent.rs:516-522). `set_model_request` accepts extension ids (validated against the extension list); unregistered id ⇒ bundled registry fallback unchanged.
- No abort signal in v0 (no per-turn AbortSignal exists in the Rust loop) — documented.

L5 (design decisions T2/WP-702, from explore mwdr9aun-4-viy7, 2026-11-12):
- Client + registry are free in the sidecar: `@earendil-works/pi-mcp` (hand-rolled, NDJSON JSON-RPC, in upstream/node_modules, imported by dist) + upstream's registerMcpServer validation/registry/`mcp_servers_change` (bound via runner.bindCore). No new Rust MCP client.
- The connection + tool registration live in the BUILT-IN mcp extension (`createMcpExtension`, exported by dist/index.js) — the sidecar must load it in handleInit (after runner, before ready), mirroring upstream main.ts extensionFactories injection (probe the factory signature with a node one-liner first).
- Bridge protocol v2 (lockstep, version bump + docs section): new sidecar→core F&F event `tools_changed {tools: [...ready.tools shape...]}` — MCP tools register after connection (post-ready) and the static ready snapshot would miss them; core replaces ctx.ext_tools on receipt. No re-init.
- Core must fire `session_start` after ready (existing cli.rs path; the mcp extension keys its lifecycle on session_start/session_shutdown) — verify it actually fires in the headless flow.
- 702c: core reads `<agent-dir>/mcp.json` (upstream shape `{"mcpServers": {...}}`), passes it in the init payload (`mcpConfig`); sidecar registers each entry through the same registerMcpServer path AFTER the mcp extension is wired (so change handlers exist). Project `<cwd>/.pi/mcp.json`: documented v0 non-goal (agent-dir only, same rule as settings.json).
- Naming: `mcp__<server>__<tool>` (upstream naming.ts, free via the extension). Exposure (`codemode` default etc.): v0 declares all MCP tools to the model regardless of exposure — no codemode in headless; documented non-goal.
- Crash semantics = upstream: no auto-restart; lazy reconnect on next call (test: fixture server dies after first call, second call reconnects + works).
- Timeouts: keep the existing core request timeout; documented. OAuth/HTTP = WP-703.
